# ohpmrc

ohpmrc is the ohpm configuration file.

#### Description

ohpm obtains its configuration from the command line and the .ohpmrc file. The **ohpm config** command is used to modify a user-level .ohpmrc file.

#### Files

-   Project-level configuration file: /path/to/my/project/.ohpmrc
-   User-level configuration file: ~/.ohpm/.ohpmrc
-   All ohpm configuration files are INI files, each of which consists of parameters in the format of <key>= <value>.

![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/06/v3/OPskxkXzQ0aCoxZmMuaH5A/caution_3.0-en-us.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=D8A6F368F19DA9B46FDAE647FA3B28C7EFE3F48DA90105BCF627FF2A3ED90633)

-   The command line tool preferentially reads the project-level configuration file. If some configuration items are missing, it reads them from the user-level configuration file.
-   You can execute the ohpm command in any subdirectory of the project to read the project-level .ohpmrc configuration.

#### Comments

In the .ohpmrc file, the number sign (#) or semicolon (;) is used as the comment character.

#### Configuration Update

Run the following command to set user-level configurations:

ohpm config set key value

#### install\_all

In the ohpm client version 1.8.0, the .ohpmrc file supports an **install\_all** configuration to control the behavior of **ohpm install**, **ohpm update**, and **ohpm uninstall**. When **install\_all** is set to **true** or left as default:

-   Running the **ohpm install** command will install all module dependencies under the project, which is consistent with running **ohpm install --all**.
-   Running the **ohpm update** command will by default update the dependencies of the current module and install all module dependencies under the project, which is consistent with running **ohpm update --all**.
-   Running the **ohpm uninstall** command will by default delete the dependencies of the current module and uninstall all module dependencies under the project, which is consistent with running **ohpm uninstall --all**.

#### resolve\_conflict

Since version 1.5.0, ohpm supports the function of automatically resolving dependency version conflicts. To enable this function, set **resolve\_conflict** to **true** or leave it as default in the .ohpmrc file. If your project depends on different versions of a third-party library, ohpm selects the latest version for installation, avoiding possible version conflicts.

![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/09/v3/i19X7zT9T7O-aFWgM9oLFA/caution_3.0-en-us.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=CE7DA00C3B889EBE208214D473F13A1694E714E92E8C5156862BFCAE4DF90975)

If a third-party library has both a remote version and a local version (local file or source code dependency), the local version is preferentially selected as the version to be installed, regardless of whether the local version is later than the remote version.

## Dependency Conflict Resolution When the ohpm install Command Is Used with the --target\_path Option

**target\_path** contains custom dependency configuration files (**oh-package.json5**) automatically generated by hvigor for each module based on the target product during the build process. For details, see [target\_path](../common-commands/ohpm-install/document.md#section79331822125611). In the generated **oh-package.json5** file, the version of the dependency may include **targetName**, for example, **"version": "1.0.0+_targetName_"**.

The complete format of the version containing **targetName** information is: <major>.<minor>.<patch>\[-<pre-release>\]\[+<targetName>\]. The conflict resolution rules are as follows:

1\. The comparison rules for the <major>.<minor>.<patch>\[-<pre-release>\] part still follow the handling rules described in the previous scenarios, that is, the dependency with the largest version number is taken.

2\. When the <major>.<minor>.<patch>\[-<pre-release>\] parts of two versions are consistent, the dependency with the \[+<targetName>\] information at the end is taken.

![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/c2/v3/AM-PvxyiTT2VkJFsf0V5iQ/caution_3.0-en-us.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=3A89AAB3BE90364A7B88A24EEDD7339E12FDD18B42D266E6409CB0B5ECF8D55F)

1\. When both versions have \[+<targetName>\] information at the end and the **targetName** values are inconsistent, the system checks whether **targetName** in the **_<target\_path>_/dependencyMap.json5** file is empty.

-   If **targetName** is empty, a warning message is printed.
-   If **targetName** has a value, an error message is displayed and the program is terminated.

2\. If one of the two dependencies is a local dependency, the local dependency is preferred; if both dependencies are local, the version configured in the **oh-package.json5** file of the local dependency package is obtained and compared again according to the above rules.

## Restrictions

1.  To resolve the dependency version conflicts of all modules in a project, run the **ohpm install --all** command to install dependencies.
2.  If you run the **ohpm update** or **ohpm uninstall** command, the original dependency version conflict processing result of the project may be damaged. In this case, run the **ohpm install --all** command to reprocess the dependency version conflicts of all modules in the current project.
3.  If conflicts occur between local file (with .har or .tgz suffix) dependencies, between local source code module dependencies, or between local file (with .har or .tgz suffix) dependencies and local source code module dependencies, the ohpm automatic conflict resolution mechanism will compare the version number configured in the **version** field of the **oh-package.json5** file inside the dependency, and the dependency with the larger version number will be installed.
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/f6/v3/ZzL8mjnwQmm0zHMZszM1BA/caution_3.0-en-us.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=9380B793FFDE7F940F56C9119DD706B4936E4B506306E766B5266494C821F18E)

#### resolve\_conflict\_strict

Since version 5.0.9, ohpm provides a strict conflict resolution mechanism for managing dependency versions. To enable this feature, set **resolve\_conflict\_strict** to **true** in the .ohpmrc file.

When strict conflict resolution is enabled, if your project depends on multiple versions of a third-party library, ohpm applies the strict conflict resolution algorithm to identify and install the most appropriate version. If ohpm cannot identify the version that meets the requirements, it reports an error.

## Strict Conflict Resolution Algorithm

-   If a dependency has a fixed version (for example, 1.0.1) and multiple range versions (for example, ^1.0.0, ~1.1.0, and >1.0.0), and the fixed version falls within the intersection of all range versions, ohpm will install that fixed version. Otherwise, conflict resolution fails.
-   If a dependency has only multiple range versions and there is an intersection among them, ohpm will install the latest version available in the repository that lies within the intersection range. If no intersection exists among the range versions, conflict resolution fails.
-   If the same local dependency (for example, ./a.har) has inconsistent paths, conflict resolution fails.
-   If a dependency has both a local version (for example, ./a.har) and a remote version (for example, ^1.0.0), conflict resolution fails.
-   If a dependency has multiple fixed versions, conflict resolution fails.
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/48/v3/hdT3NdheRVm8WOkfWX_D_Q/en-us_image_0000002532670201.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=0F6F3022B908F8811340302EBCAA4B32502DDA1D8FB6E2C0BC7FFFE7A670A19E "Click to enlarge")

1.  When a conflict is successfully resolved, ohpm displays a warning message that includes the dependency name, all conflicting versions, the installed version, and a list of affected modules.
2.  When a conflict cannot be resolved, ohpm prints the dependency conflict tree, highlights the dependencies and their versions that fail to be resolved, and displays the error messages of such dependencies, including the dependency names and all conflicting versions. #### key\_passphrase

Since version 5.2.0, the ohpm client has supported configuring **key\_passphrase** (private key password) in the **.ohpmrc** file, which is used to automatically decrypt the private key file corresponding to **key\_path**.

-   When you run commands that require authentication, such as **ohpm publish** or **ohpm unpublish**, the system automatically uses **key\_passphrase** to decrypt the private key.
-   **key\_passphrase** must be the ciphertext generated by running the [ohpm config encrypt](../common-commands/ohpm-config/document.md#section1085417514102) command.
-   **key\_path** (private key file path) must be configured.

key\_passphrase=security:xxx

#### AccessToken

AccessToken is a new authentication mechanism introduced in ohpm-repo 2.1.0. You can generate a token on the ohpm-repo page and add it to the configuration file of the ohpm client.

When interacting with ohpm-repo, the client automatically packs a token for identity authentication. The token has two permission levels:

1.  Read-only tokens allow the execution of **ohpm info** and **ohpm install** commands.
2.  In addition to the read-only permissions, read-write tokens support **ohpm publish** and **ohpm unpublish** commands.

A maximum of 10 tokens can be generated for each permission type. When a token is generated for the first time, the system automatically copies it to the clipboard and does not display the complete token content later.

#### enforce\_dependency\_key

Since ohpm 1.7.0, ohpm supports configuring **enforce\_dependency\_key** in the **.ohpmrc** file. The value of this configuration item is of the boolean type, with a default value of **false**. If the configuration is set to **true**, ohpm verifies whether the names of local dependencies in the **oh-package.json5** file of each module match their corresponding package names (module names). If there is a discrepancy, it will cause the dependency installation to fail and print out the inconsistent dependency names and their corresponding package names (module names) in the error log.

**Example**

There is a module named **foo** in the **MyApplication** project. The **oh-package.json5** file of the **foo** module contains the following content:

{
  "name": "foo",
  "version": "2.0.0",
  "description": "Please describe the basic information.",
 }

There is another module named **bar** in the **MyApplication** project, and the **bar** module depends on the **foo** module. The **oh-package.json5** file of the **bar** module contains the following content:

{
  "name": "bar",
  "version": "1.0.0",
  "description": "Please describe the basic information.",
  "dependencies": {
    "fee": "file:../foo"  
  },
 }

As shown above, the dependency on the **foo** module is configured in the **oh-package.json5** file of the **bar** module, and an alias **fee** is created for the **foo** module. When **enforce\_dependency\_key** is set to **true** in .ohpmrc:

enforce\_dependency\_key=true

If you run the **ohpm install --all** command in **MyApplication**, the following error log is displayed and the command execution is interrupted:

ohpm ERROR: local dependency "fee" found in "D:\\DevecostudioProjects\\MyApplication2\\bar\\oh-package.json5" does not match the actual name "foo" of its oh-package.json5
ohpm ERROR: Install failed, detail: There are some dependency names that are inconsistent with the actual package names.

If **enforce\_dependency\_key** is not set or is set to **false**, the command will not be interrupted, and the log level of the preceding error logs will be lowered to warn.

ohpm WARN: local dependency "fee" found in "D:\\DevecostudioProjects\\MyApplication2\\bar\\oh-package.json5" does not match the actual name "foo" of its oh-package.json5

You are advised to set **enforce\_dependency\_key** to **true**, and do not configure local dependencies using aliases to avoid the following scenarios.

There is a module named **fee** in **MyApplication**, and the version of this module is earlier than that of the **foo** module. The **oh-package.json5** file of the **fee** module contains the following content:

{
  "name": "fee",
  "version": "1.0.0",  // The version number is earlier than 2.0.0 of foo.
  "description": "Please describe the basic information.",
 }

The **entry** module depends on both the **fee** and **bar** modules. The dependency configuration in the **oh-package.json5** file of the **entry** module is as follows:

{
  "name": "entry",
  "version": "1.0.0",
  "dependencies": {
    "fee": "file:../fee",
    "bar": "file:../bar"  
  },
 }

In the dependency tree of the **entry** module, there are two versions of a dependency named **fee**: one is the **foo** module with the alias **fee**, and the other is the **fee** module itself. #### compability\_log\_level

**compability\_log\_level** is supported since ohpm 5.0.1. It is used to control the behavior of ohpm when the fields required for compatibility testing are missing.

The default value of **compability\_log\_level** is **warn**. For details about the available values, see [Values of compability\_log\_level](#section139481140114517).

When executing the **prepublish** and **publish** commands, ohpm checks whether all the fields required for compatibility testing (**compatibleSdkVersion**, **compatibleSdkType**, **obfuscated**, and **nativeComponents**) are configured in the **oh-package.json5** file. For details, see [Fields in the Module-level oh-package.json5 File](../oh-package-json5/document.md#en-us_topic_0000001792256137_oh-packagejson5-%E5%AD%97%E6%AE%B5%E8%AF%B4%E6%98%8E). If any of the fields is not configured, ohpm displays a message or reports an error based on the log level.

## Values of compability\_log\_level

-   **close**: The fields required for compatibility testing are not checked.
-   **info**: If any field required for compatibility testing is not configured, an info log is printed.
-   **warn**: If any field required for compatibility testing is not configured, a warn log is printed.
-   **error**: If any field required for compatibility testing is not configured, an error message is displayed and the program is terminated.

#### enable\_unified\_lockfile

The **enable\_unified\_lockfile** field is added to the ohpm client since 5.1.1. If this field is set to **true**, ohpm automatically integrates the **oh-package-lock.json5** files of all submodules in the project to the **oh-package-lock.json5** file in the root directory of the project.

If **enable\_unified\_lockfile** is set to **true**, the **lockfile** files are managed in a unified manner at the project level. If there are repeated dependencies between modules, the ohpm install command execution duration is significantly reduced, optimizing the build process.

If **enable\_unified\_lockfile** is set to **true**, the .hsp dependency installation directories of each module are migrated to the root directory of the project. When this feature is enabled on the pipeline, it must be used with Hvigor.

#### enable\_boost\_extraction\_speed

Since ohpm 5.3.0, the **enable\_boost\_extraction\_speed** field is supported. ohpm installation involves decompression and traversal of third-party package files in .har or .tgz format. After this feature is enabled, a high-performance method is used for decompression and traversal. If the project has large file dependencies, the execution time of **ohpm install** can be significantly reduced. This feature is currently in the experimental phase and does not yet support decompressing third-party package files that contain symbolic links.

#### enable\_lock\_inner\_pkg\_version

Since ohpm 5.3.1, the **enable\_lock\_inner\_pkg\_version** field is supported. This field defaults to **true**. If it is set to **false**, during ohpm installation, the versions of internal .har or .tgz sub-dependencies will not be saved to the **oh-package-lock.json5** file. This prevents the lock file from storing invalid paths that could cause errors during subsequent installations.

As shown in the figure below, the blue arrow indicates the final dependency to be installed. Dependency **D@1.0.0** comes from dependency **B@1.0.0** (dependencies with the same name and version are treated as identical, and the final installed version is determined by the build order). Since **B@1.0.0** is not installed, and the version of dependency D is locked in **oh-package-lock.json5**, a "dependency path not found" error will occur during reinstallation. In such cases, set this field to **false**.

#### case\_sensitive\_check

Since ohpm 6.21.0, the **case\_sensitive\_check** field is supported. If this parameter is set to **true**, during execution of ohpm commands, ohpm will throw an error to prompt you to modify the inconsistency if it detects case mismatches between the configured paths of files in the project and their actual paths. This configuration item takes effect only in the Windows environment.

**Detection Scope**

-   Paths of the .har package, .tgz package, and module used as dependencies in the project.
-   Directories or paths configured in commands for **prefix**, **target\_path**, and **parameterFile**.
-   Local dependency paths in the **overrides** configuration, configuration files involved in **overrideDependencyMap** and their internal local dependency paths, and **parameterFile** configuration files and their internal local dependency paths.

**Example**

1.  Prepare a local .har package **test.har**. In the **oh-package.json5** file inside this .har package, set the **name** field to **test**. Place this package in the **libs** directory of the entry module.
2.  Configure the entry module to depend on **test.har**. The original dependency path is: **_<project\_dir>_/entry/libs/test.har**. The content of entry's **oh-package.json5** is as follows:
    
    {
      "name": "entry",
      "version": "1.0.0",
      "description": "Please describe the basic information.",
      "dependencies": {
        "test": "./Libs/test.har"
      }
    }
    
3.  Run **ohpm install**. ohpm will detect a case mismatch between the actual path of **test.har** (**_<project\_dir>_/entry/libs/test.har**) and the configured path (**_<project\_dir>_/entry/Libs/test.har**). Specifically, the configured directory name **Libs** uses an uppercase "L", which does not match the original directory name **libs**. At this point, ohpm will throw an error with a prompt and abort execution.
