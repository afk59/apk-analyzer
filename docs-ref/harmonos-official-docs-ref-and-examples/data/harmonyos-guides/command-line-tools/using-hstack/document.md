# Using hstack

#### Description

hstack is a tool to help you deobfuscate crash stacks from release apps and restore them to the corresponding source code stacks. It supports Windows, macOS, and Linux platforms. For details on the principles of stack trace parsing, see [Exception Stack Trace Analysis](../../coding-and-debugging/analyzing-logs-and-faults/fault-analysis/exception-stack-trace-analysis/document.md).

The hstack command format is as follows:

hstack \[options\]

**options**: indicates available configurations. For details, see [hstack command configurations](#table25697717185).

#### Example

1.  Archive the crash files generated by the app to the **crashDir** directory (or specify a crash stack via **\-c**). For details about how to obtain the stack, see [Crash Detection](../../system/debugging-tools/performance-analysis-kit/fault-detection/overview/document.md).
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/de/v3/AnBGY1qaRP6N89qC6lM0oQ/en-us_image_0000002501069946.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=780BF1C6CB3B4717B67A46A89B8A663BBE6F2DA2EDDEAAF563DBE7BBF3A7733D)
    
2.  Use **\-o** to specify the output directory. If it is not provided, the result is output to the **crashDir** directory specified by **\-i**. (When the input is a crash stack specified by **\-c**, you can use **\-o** to specify an output file; or you can omit it, and the results will be directly output to the console.)
3.  Use **\-s** to specify the archive directory of the **sourceMap** file of the project. (This parameter is optional. One or both of the archive directories for **sourceMap** files and shared object files must be provided.)
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/4c/v3/qk2ffJ_pQHG7-u7EtzpBsg/en-us_image_0000002500910112.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=CBDB567BE820BAC9117EF6FF66E0F64E832165164DD3251463FD6965C8CAC115)
    
4.  Use **\--so** to specify the archive directory of the shared object file. (This parameter is optional. One or both of the archive directories for **sourceMap** files and shared object files must be provided.)
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/50/v3/ANI2XVs-QvqQjW6YQEfMoA/en-us_image_0000002500910106.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=41934322AF7E7F2CD9B66513617CD71D6299C07D5772AFCB09F83B25C241CE4D)
    
5.  (Optional) Use **\-n** to specify the nameCache file archive directory.
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/c1/v3/yXkmh9gbTym9tSs2X8hPdA/en-us_image_0000002501069954.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=C20E7E32A7EB350C394CCB02B52A49C9C02547E07C4F28CE0C8C758BE96DC628)
    
6.  Run the following command to deobfuscate the crash stack of the release app, restore it to the corresponding source code stack, and save the parsed result to the **outputDir** directory:
    
    hstack -i crashDir -o outputDir -s sourcemapDir --so soDir -n nameCacheDir
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/48/v3/ptpZpguURKq1ShSAPweK-g/en-us_image_0000002532749989.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=B9E5F15907B2BC52EC0A2F6711A309D4CA441439B81D140757383D49A3EAD90F)
    
    After the parsing is complete, the corresponding parsing result file is generated in the **outputDir** directory. The file is named after the original crash file and prefixed with an underscore (\_). The C++ logs and ArkTS logs in the crash stack have been parsed into the file path, row number, and column number corresponding to the source code, as shown in the following figure.
    
    ![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/99/v3/cO7JNmkHSVCIua364ZQwWQ/en-us_image_0000002500910108.png?HW-CC-KV=V1&amp;HW-CC-Date=20260410T062159Z&amp;HW-CC-Expire=86400&amp;HW-CC-Sign=C807A57A3206DA4C043DE49D0303E452EBB26908B5649AAADF9EA9057A7F45E0)
    
    Note: When a release app is built, the .so file does not contain symbol table information by default. To generate a .so file that contains symbol table information, set **buildOption** in the module's **build-profile.json5** file of the project as follows:
    
    "buildOption": {
      "externalNativeOptions": {
        "arguments": "-DCMAKE\_BUILD\_TYPE=RelWithDebInfo"
      }
    }
    

#### Stack Parsing Solution Description

The following code is used as an example.

In this example, the **Entry** module references the **har** method in the **har** module through an independent **har** file.

import {har} from 'Har'
@Entry
@Component
struct Index {
  @State har: string = 'Har';
  build() {
    Row() {
      Column() {
        Text(this.har)
          .fontSize(50)
          .fontWeight(FontWeight.Bold)
          .onClick(() => {
            let entryClass = new EntryClass();
            entryClass.callHarFunction();
          })
      }
      .width('100%')
    }
    .height('100%')
  }
}

class EntryClass {
  callHarFunction() {
    har()
  }
}

@Component
export struct MainPage {
  @State message: string = 'Hello World';

  build() {
    Row() {
      Column() {
        Text(this.message)
          .fontSize(50)
          .fontWeight(FontWeight.Bold)
      }
      .width('100%')
    }
    .height('100%')
  }
}

export function har() {
  BigInt(1.1)
}

The generated crash report is as follows:

at har (entry|har|1.0.0|src/main/ets/components/mainpage/MainPage.js:58:58)
at i (entry|entry|1.0.0|src/main/ets/pages/Index.ts:71:71)
at anonymous (entry|entry|1.0.0|src/main/ets/pages/Index.ts:55:55)

The crash report contains obfuscated method names (or property names), path information, and obfuscated line and column number information, where:

-   The method names are obfuscated after the corresponding obfuscation rules are configured (for example, **callHarFunction** in **EntryClass** is obfuscated to **i** in the above example). The mapping relationship between the obfuscated and non-obfuscated method names is saved in the nameCache file of the corresponding module's build product.
-   The path information follows the format: **referring entry-packageName|referenced packageName|version|relative source code path**, where **packageName** and **version** are saved in the **sourceMap** file of the corresponding module's build product.
-   The mapping relationship between the obfuscated and original line and column numbers is saved in the **sourceMap** file of the corresponding module's build product. You can parse the **mappings** field in the file to restore the original line/column numbers from the obfuscated ones.

To restore a stack, perform the following steps:

1.  Locate the **sourceMap** file of the referencing module using its path information. For example, the first stack trace:
    
    at har (entry|har|1.0.0|src/main/ets/components/mainpage/MainPage.js:58:58)
    
    You can find the following fields in the **sourceMap** file of the entry module at **entry|har|1.0.0|src/main/ets/components/mainpage/MainPage.js**:

        "version": 3,
        "file": "MainPage.js",
        "sources": \[
          "oh\_modules/.ohpm/Har@ue9rwlwgmslvadnmypsedjcin6a=/oh\_modules/Har/src/main/ets/components/mainpage/MainPage.js"

        "entry-package-info": "entry|1.0.0",
        "package-info": "har|1.0.0"

2.  Use the corresponding source map information to restore the stack trace path, line number, and column number.
    
    Based on the source map information obtained in step 1, parse the **sources** and **mappings** fields to restore the details as follows:
    
    at har (oh\_modules/.ohpm/Har@ue9rwlwgmslvadnmypsedjcin6a=/oh\_modules/Har/src/main/ets/components/mainpage/MainPage.js:58:58)
    
    The file is in the **oh\_modules** directory of the **entry** module.
    
    If the corresponding **sourceMap** file contains the **package-info** field, you can use the **sourceMap** file of the corresponding module in the **package-info** to perform a secondary parsing on this stack trace. For example, if **package-info** in this stack trace is **har|1.0.0**, you can use the **sourceMap** file in the **har** module to parse this stack trace again, with the solution as follows:
    
    1.  Starting from the last **oh\_modules** in the path, go down two levels and truncate the path from the first parsing result. The result is as follows:
        
        src/main/ets/components/mainpage/MainPage.js
        
    2.  Concatenate the preceding path with **package-info** to form a new path: packageName|packageName|version|truncatedPath. The obtained path in this example is as follows:
        
        har|har|1.0.0|src/main/ets/components/mainpage/MainPage.js
        
    3.  Using the concatenated path, find the following field in the **sourceMap** file of the **har** module:
        
        "har|har|1.0.0|src/main/ets/components/mainpage/MainPage.js": {
          "version": 3,
          "file": "MainPage.ets",
          "sources": \[
            "har/src/main/ets/components/mainpage/MainPage.ets"
          \],
          "names": \[\],
          "mappings": ";;;AAEA,MAAA,OAAA,QAAA,SAAA,MAAA;IADA,YAAA,CAAA,EAAA,CAAA,EAAA,CAAA,EAAA,IAAA,CAAA,CAAA,EAAA,IAAA,SAAA,EAAA,CAAA;;;;;;;;IADyB,CAAA;;;;;;;;;;;;;;;;;;;;;;IAKvB,aAAA;;;;;;;;;;;;YAGM,IAAA,CAAA,UAAA,CAAA,UAAA,CAAA,IAAA,CAAA,CAAA;;;;;IAOL,CAAA;;;;;AAGH,MAAA,UAAA,GAAA;;AAEA,CAAA",
          "entry-package-info": "har|1.0.0"
        }
        
    4.  Parse the **sources** and **mappings** fields in the **sourceMap** file to obtain the source code information.
        
        at har (har/src/main/ets/components/mainpage/MainPage.ets:20:1)
        
    
3.  Use the nameCache file to resolve and restore the method name.
    
    The following uses the second stack as an example:
    
    at i (entry|entry|1.0.0|src/main/ets/pages/Index.ts:71:71)
    
    After steps 1 and 2, the path, row number, and column number information of the stack trace are restored as follows:
    
    at i (entry/src/main/ets/pages/Index.ets:25:3)
    
    In the nameCache file of the corresponding module's build product, find the following field through the resolved file path:
    
    "entry/src/main/ets/pages/Index.ets": {
      "IdentifierCache": {
        "Index#initialRender#\_\_function": "o",
        "Index#initialRender#$2#\_\_function": "t",
        "Index#initialRender#$2#$0#entryClass": "u",
        "$0#\_\_function": "a1"
      },
      "MemberMethodCache": {
        "initialRender:6:20": "initialRender",
        "callHarFunction:24:26": "i"
      },
      "obfName": "entry/src/main/ets/pages/Index.ets"
    }
    
    **IdentifierCache** and **MemberMethodCache** in this field save the mapping relationship between the original and obfuscated method names, with the format as follows:
    
    "Original method name: starting line number of the method: ending line number of the method": "Obfuscated method name"
    
    The obfuscated method name in the second stack trace is **i**. Use the above field to restore the method name:
    
    1.  Look up all entries in the **IdentifierCache** and **MemberMethodCache** fields where the obfuscated method name matches "i". In this example, the matching entry is as follows:
        
        "callHarFunction:24:26": "i"
        
    2.  Determine which entry's line number range includes the line number obtained from step 2. In this example, the restored line number is 25, and it falls within the range 24–26, then the original method name is "callHarFunction."
    
    By the above method, the original method name of the source code can be obtained.
    
4.  Integrate the results obtained in steps 2 and 3 to get the final stack trace result as follows:
    
    at har (har/src/main/ets/components/mainpage/MainPage.ets:20:1)
    at callHarFunction (entry/src/main/ets/pages/Index.ets:25:3)
    at anonymous (entry/src/main/ets/pages/Index.ets:14:47)
    

In the foregoing manner, the crash information of the release app may be parsed and restored by using the build product.
